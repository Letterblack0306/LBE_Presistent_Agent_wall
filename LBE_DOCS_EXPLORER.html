LBE Reference & TUI Implementation Workbench

Guidance and illustrative examples; verify against the live repository and runtime before action.

Purpose and reading order

Use this page to choose the right references for a specific LBE area and review interaction samples. It does not supersede existing implementation, machine policy, branch state or evidence records. The adjacent original graph primarily contains a historical Guard Inspector design.

1 · Product intent

Documentation router → Product intent owner → Agent lifecycle.

2 · Source & ownership

Structural owner index → Complete document inventory → actual code in Rust TUI source and Python backend.

3 · Plan & governance

Implementation plan → Intent ledger → Machine gate.

4 · Evidence, not labels

Dated status → Acceptance collection → real terminal/provider/receipts. A green test alone is not proof the installed product works.

Source hierarchy: live runtime/observed effects → active workspace source + Git HEAD → governance/owners → documentation → external references and chat history. “Documented,” “coded,” “unit-tested,” and “runtime-proven” are different states.

Scope of this workbench

Design planning, source routing and terminal samples only. No sample below represents an actual screenshot of the current LBE installation, and no cross-project feature is assumed to exist merely because a reference implements it. Branch availability/status must be read from Git, not inferred from old branch names.

For each area: inspect current owning code, compare only verified upstream behavior, record a bounded discrepancy, implement through the existing authority owner, then validate the installed result. These are proposed assessment steps, not completed implementation.

Workspace browser behavior required before implementation

Keyboard-first tree navigation (Up/Down, Left/Right expand, Enter inspect, Esc return), file filtering, active-file focus, dirty/modified markers from Git, long-path truncation, workspace-root enforcement and responsive collapse. Real files and directory contents must come from the current governed workspace, not hand-maintained HTML or historical documentation. Selecting a file should inspect content through the authorized file-read path; no write action is implied by navigation.

Classifications: PROVEN, DISPROVEN, INCONCLUSIVE, BLOCKED_CONFIGURATION, STALE_TEST_OR_FIXTURE, TEST_HARNESS_FAILURE. Do not say READY on the basis of an external sample, a passing unit test, a pretty UI, or the presence of a file.

Workspace hygiene

Do not delete, reset, or move unknown untracked files. Review all document and branch consumers before consolidation. Preserve old proof with date and revision. HTTP serving of the entire repository can expose internal files; use loopback-only, controlled access, and avoid exposing sensitive paths.
